# Loopit Tracking Plan

将 Loopit PRD 转化为 TE（ThinkingData／数数）埋点方案。默认完成需求分析、只读核查和方案输出；修改 TE 元数据、飞书、代码或生产系统不属于默认任务范围。

## 工作流程

1. **理解需求与统计目标。** 读取 PRD，识别用户行为、业务对象、关键转化和成功/失败状态。按指标目标划分统计页面与模块，不先从组件清单机械生成埋点。
2. **按需查阅依据。** 先使用本 skill 已固化的稳定规则和本次会话已核实的证据；按 [source-docs.md](references/source-docs.md) 的分工，在定义未覆盖、出现冲突或需要确认最新约定时读取对应飞书章节，不要求每次完整重读规范和预定义文档。
3. **核查已有采集。** 有 TE 访问条件时按 [api.md](references/api.md) 主动查询尚未核实的事件及候选属性；可复用本次会话中仍适用的查询结果，涉及新名称、定义变化或用户要求最新状态时再查。命名、触发时机、属性来源不清楚时查代码。涉及 RN、Native 或 H5 时按 [rn-analytics.md](references/rn-analytics.md) 追踪到实际消费者、上下文快照、字段转换和各投递目标，不以调用 `track()` 代替出网核查。区分团队约定、已核实元数据、当前实现、方案拟定和未核实项，不把查询失败当成不存在。
4. **作出设计决策。** 先列需要回答的指标问题，再选择足够支持这些指标的采集点和属性。分别决定采集点新增/更新、事件复用/独立、属性复用及实体绑定。给出可实施的名称，不因缺少现成名称就要求用户命名。
5. **输出方案。** 使用 [output-format.md](references/output-format.md) 的标准表，说明触发、计数、必要归因及待确认差异。涉及跨端漏斗或既有点位验收时，补充[漏斗与字段取证](references/output-format.md#funnel-and-property-evidence)。需求外的建议补充项单独标明。搜索和历史案例仅按需参考 [examples.md](references/examples.md)。
6. **仅在明确请求时执行写入。** TE 元数据写入前按 api.md 展示具体变更，并获得针对该次写入的确认。

## 信息来源与维护

本地 skill 保存稳定方法和已确认决策；飞书维护团队完整规范与预定义清单；TE 核实实际事件和属性；代码解释实现、触发与字段来源。四者不是单一的优先级排序，差异处理和查阅入口见 [source-docs.md](references/source-docs.md)。

用户在当前任务明确给出的口径优先适用于当前方案。旧文档、代码或案例与之冲突时说明差异；不据此宣称线上已变更。更新 skill 时沉淀稳定规则，具体功能枚举放案例并标日期/状态，不复制整套飞书规范，也不自动同步外部文档。

## 统计页面与命名

- 埋点的页面是服务指标统计的**统计页面**，不要求与物理页面、路由、组件一一对应；一个物理页面可承载多个统计页面，多个物理页面也可按统计目标归为一个页面。
- 定位页面、模块、元素时，可先查《预定义埋点》，再从代码中的埋点调用、常量、路由、组件理解和借鉴。代码用于核实当前实现，不自动决定目标统计口径。文档、代码、统计目标有差异时明确说明，不机械照搬。
- 优先复用统计语义一致的标识。无可用参考时，根据需求和已有命名风格给出明确名称并标注“拟定”；代码不可访问时标注未核实。
- 每个采集点明确 `page_id`，不能只写“入口所属页面”或“如 explore_page”。多入口逐一给出映射或分行。实现定位字段（如既有 `page_name`）与统计页面标识分开理解。
- 代码位置优先使用本次任务明确指定的仓库或工作树，否则读取 `~/.config/loopit/workspace.json` 的 `repositories.frontend`、`repositories.backend`；格式见 [workspace-config.md](references/workspace-config.md)。查代码前核实目录、仓库身份和当前分支；路径缺失或无效时说明代码未核实，不硬编码个人路径或自动切换分支。

## 采集点与事件选择

采集点新增/更新、事件新增/复用、属性新增/复用三个判断分别说明；下表中的采集点判断不能替代事件或属性的复用结论：

| 判断 | 规则 |
| --- | --- |
| 新增采集点 | 新接入页面、模块、元素或行为采集，即使复用 TE 事件名，也写“新增” |
| 更新采集点 | 修改已存在采集点的属性、取值或触发口径，写“更新” |
| 页面曝光 | 统一复用 `a_page_exp`，不设计 `element_exposure` 加 `element_type=page` 的新方案 |
| 低重要性元素 | 事件量小且分析重要性低时，曝光复用 `element_exposure`，点击复用 `element_click` |
| 高重要性行为 | 核心分析对象优先独立业务事件；先查是否已有同义事件，独立曝光、点击使用 `_exp`、`_clk` 后缀 |

事件独立不意味着属性也要新建。已有自动采集或通用采集可满足需求时应接入并补齐上下文，避免重复发送；不自动迁移、删除存量事件。

## 属性与业务实体

- 先查 TE 既有属性和当前实际采集，再按业务语义寻找可复用属性。语义、类型及取值口径兼容时尽量沿用同一个已有名称，无论缩写还是全称；不把已有缩写统一改成全称，也不为同一维度再建同义属性。
- 核查确认没有对应语义的合适属性时，才拟新增全称属性；查询失败或空结果不能直接证明不存在。仍须满足下述分析必要性及 raw 规则，不因此无条件新增顶层字段。
- 方案明确标识每个属性是复用、拟新增还是证据不足待核查。复用时指出参考哪个既有事件/采集链路、哪个属性，以及兼容的语义、类型、取值；字段映射只是依据，不能只补全称到缩写的对照表就结束。
- 明确用于看板且无合适现有属性时，才考虑新增顶层属性。非看板所需、低复用数据放入 `raw` JSON 字符串；`tags` 沿用已有染色及链路关联用途，不作为无限扩展字段的替代品。
- `source` 默认表示上一个**统计页面的 `page_id`**。同页元素沿用该页的进入来源；跨统计页面后指向离开的统计页面。不用它表示输入方式、按钮类型或搜索发起方式。
- 触发来源先查已有同义属性（包括 `trigger_source`、`tr_src`）；兼容时沿用该链路已有名称，不为统一成全称而重命名或新建。核对语义后再选取值，不为同一维度并列创建 `search_source`、`submit_method`、`trigger_type`。若后续事件透传最初触发来源，明确业务过程、传递范围和重置时机，不与后续动作自身来源混淆。
- **属性按分析需要落点，不沿链路无差别重复上报。** 入口事件或 element_id 已能区分触发操作时，入口无需再带相同含义的 trigger_source；客户端仍在实际触发时确定并传递上下文，在结果侧需要分组分析的事件上报。采集点不填某属性，不等于客户端不维护该上下文；具体搜索用法见 examples.md。
- `entity_type/entity_id` 只绑定明确业务对象，例如 `project` 与作品 ID。没有必要绑定的模块、Tab 不填写自身实体；用 `module_id`、`element_id` 标识位置。文本、标签实体须明确实际内容来源，具体案例见 examples.md。
- 查属性成功不等于已验证所有枚举、类型或目标事件关联。借鉴代码时检查出网字段映射，避免逻辑同名但落到另一物理属性。

## 触发与计数

- 区分页面到达、内容可见、用户点击、业务成功和失败；页面曝光不代表加载成功，默认选中不伪造点击。
- 曝光以实际可见为依据，隐藏、骨架、预加载不直接计曝光。阈值、去重周期、返回和重进是否计数，应参考已有规范并结合统计目标明确，不把某次示例规则推广成全局标准。
- 涉及转化时明确分母、关联对象和归因范围。若只具备来源页面，不能声称已能逐次关联点击与到达；需要关联字段时先查可复用属性。

## 异步归因与业务结果

仅在需求涉及异步提交、跨页结果或恢复时应用，不给所有需求强加订单、trace 或全链路字段。

- 明确上下文 owner、冻结时点和有效期；按需要保留原账号、环境、业务对象、统计页面/来源、业务关联 ID、业务发生时间及已有染色快照。跨作品、关闭页面、切号、重启后不得读取当前上下文冒充原始归因；缺失时标未知。区分客户端需维护的上下文与每个事件实际上传的属性。
- 原账号归因不等于授权把当前 SDK 身份改回旧账号。分别核查传输身份、事件属性和目标服务的接收策略；环境/账本校验不等于埋点路由已隔离。
- UI 反馈、SDK 回调、请求成功与权威业务终态分别定义。取消、处理中/待确认、确定失败分开；超时和未知结果不计确定失败，查单/恢复不计新业务提交。金融类成功以服务端确认交付/入账为准，重放不得重复计成功。
- 分别说明访问/曝光去重、行为重复、业务结果幂等、传输重试去重；随机 event_id、SDK 接收或队列持久化均不能单独证明业务只计一次。跨事件缺少有效关联键时，不声称可还原严格逐次漏斗。
- IAP 的历史设计、九列示例和验收边界按需读取 [commerce-example.md](references/commerce-example.md)。复用前核对目标版本、环境和实际事件契约。

## 交付检查

- 一行一个事件；曝光与点击分行，不能合并事件名。
- 新增点完整列必要业务属性，更新点仅写增量，遵守 output-format.md；“完整”不意味着填满属性清单或每个节点都重复上报。
- `page_id` 明确；来源字段不混用；实体绑定有业务意义；拟定值不冒充已有定义。
- 已分别说明采集点新增/更新、事件新增/复用、属性新增/复用及其依据；展示名或备注缺失不作为新建同义事件的理由。
- 按团队规范核对单事件新增属性数量；超过 5 个需联系张晓东确认，新事件需登记维护表，入口见 source-docs.md。仅输出所需协作/登记项，不自动发送或写表。
- 需要时附逻辑名/出网名/目标/类型、原始归因及验收矩阵；区分源码事实、静态检查、运行出网、目标收件和线上数据，未验证不写通过。
- 关键触发、计数和成功/失败口径足以支撑需求指标；不虚构实现细节。

## 访问与变更边界

TE 默认读取 `~/.config/loopit/workspace.json` 的 `thinkingdata` 配置；该文件不存在或没有该节时，整组回退到 `TEA_OPEN_BASE_URL`、`TEA_OPEN_TOKEN`、`TEA_OPEN_PROJECT_ID`，不混用两处配置。格式与错误处理见 [workspace-config.md](references/workspace-config.md)。必填项缺失时不调用 API，说明缺少的配置键并继续有依据的离线方案。token 仅在明确授权时写入该本地私有配置，不复制到 skill、仓库、日志、命令输出、文档或回答；示例使用 `{token}`。

方案中的拟定名称或枚举不等于授权修改共享定义。写入 TE 前须展示 endpoint、准确 JSON、目标事件/属性、前后含义和约束，并取得该次写入确认；详见 api.md。
