# 最小完整改动的细判

在多文件、混合 hunk、重构、移动、抽象或支撑清理需要细判时读取；普通局部审查使用入口的反事实规则即可。

## 分类及反事实

| 结论 | 判断依据 |
| --- | --- |
| 必要 | 移除直接破坏当前需求、契约、构建、兼容性或必要验证 |
| 有条件必要 | 仅特定平台、数据、后端契约、发布方式或关联改动成立时需要，明确条件 |
| 冗余 | 无独立贡献；移除后行为、契约、构建、迁移和必要验证不变，或已由同轮其他变化完整覆盖 |
| 过度改动 | 有效但超当前目标：提前通用化、顺带重构、扩大主流程或无当前消费者的未来能力 |
| 证据不足 | 缺目标、消费者、依赖或失败语义，写最小补证据动作 |

不要用“非必要”混淆冗余与过度；不能区分就写证据不足。必要但实现不合理、实现合理但超范围都可能成立。

- 目标须来自用户/需求/issue/提交说明等独立依据，不能从 diff 反推后自证。
- 每个可独立 hunk 有一个可说明的理由，混入无关功能、治理或修复分别标过度或待确认。
- 固定保留其余改动、反事实移除本项，检查目标行为、既有契约、构建兼容、数据安全、双端一致性和必要验证。
- 同一文件可含必要与过度 hunk；整体必要不覆盖局部扩张，局部冗余不否定整文件。
- 错误处理/清理配对、类型闭合、迁移、平台接线和直接相关测试即使用户不可见也可能必要，先说明移除失败。
- 局部方案未被证伪却扩展主流程、多个核心模块、新状态机或通用框架，至少标“高疑似过度改动”及缺失的必要性证据；不凭文件数量或复杂程度定罪。

## 职责与位置

1. 保持已有文件、方法、语句位置。只有目标行为、语言/框架、依赖方向或测试接线确实要求才移动，否则重排、改名、格式化、目录迁移和搬运不是必要增量。
2. 只有新增具有当前消费者的独立方法，且不改既有入口、调用、条件、状态、副作用、返回契约，才算“仅新增独立方法”。其余触达都解释为何不能保持原行为、保持后如何失败，并给影响场景/影响点/对应验证。
3. 清晰输入输出与单一 owner 的独立新逻辑默认放职责明确的独立文件，原 owner 只保留必要导入、调用、注册或渲染；不借隔离移动旧逻辑。
4. 只用一次不充分证明无需隔离，出现两次不充分证明应抽象。空壳 wrapper、重复转发、无稳定边界通用层、未来扩展点和无消费者导出属于冗余或过度。
5. 判断职责和文件数量是两回事，小文件减少旧 owner 侵入且无额外抽象可更小、更安全；“更整洁/更健壮/以后需要”不是本次门禁依据。

## 反向依赖

- 以最终 diff 查新增文件、导出、配置、mock、依赖、bridge、feature flag、兼容分支、临时日志、生成支撑的真实消费者，同轮替代实现的旧支撑尤其容易遗留。
- 找不到消费者，或等价移除后行为不变且直接验证通过，判冗余。特殊支撑至少说明消费者、移除失败和对应验证。
- 可在安全临时环境做独立删减 A/B 与直接验证；不能试验时用消费者和失败语义判断，不修改业务工作区或机械逐行删减。
- 建议移出本次改动、回退局部 hunk 或另立任务即可；未要求方案不扩展重构设计。

## 已有能力与同类代码的范围判断

1. **先找真正缺失的环节。** 沿目标输入的生产者、传递链与消费者对照基线。生产者已经提供目标能力、缺口只在消费者时，保留生产者的识别规则、资源清理与公共协议，只审目标消费者的最小接线；不能把“文件参与链路”当成必须修改。
2. **修复有效不等于本次必要。** 基线中的独立缺陷即使能被新测试复现，也不自动进入当前需求。已证明保留基线仍能满足当前目标时，无独立贡献判冗余；有贡献但解决另一目标判过度改动，不能仅以“顺便更稳健”改称有条件必要。确有适用条件且属于当前目标时，才使用有条件必要，并写明条件证据。
3. **类比扩大核对，不扩大写入。** 遇到另一平台、相邻 helper 或同类文件，逐项核对真实消费者、原合同与不改的后果。相似结构、同名方法、别处已有某种写法以及单侧发现的缺陷，都不是成批同步、补保护、清理或重构的授权；没有当前目标的独立因果就保持原样。
4. **用最小对照区分能力与支撑。** 必要时比较基线、当前实现与只保留目标接线的最小候选，复用直接相关的测试或内存对照。分别判断目标是否达成和额外修复是否有效；只为额外修复新增的测试不能反过来证明它必须留在本次交付中。
5. **撤回按同一边界收口。** 用户认定非必要后，撤回该项及专属测试、版本标记、未用参数和格式整理；保留其他需求仍需要的逻辑与回归。不得为让额外测试通过再次恢复已否定的实现，也不得由本处结论扩大为全仓同类清理。

例如：基线已采集六类动作，需求只扩展哪些动作触发播放时，采集脚本中的双指 RAF 清理是独立修复。它有效，但不能据此把脚本版本更新、资源清理或另一端同步列为该消费需求的必要支撑。

## 已有门槛与防御改动

命中新增/收紧 guard、加载/就绪判断、空值拒绝或下游二次校验时，先填写这一行审查依据，再判断必要性：

| 当前需求允许变化 | 真实生产入口与既有门槛 owner | 新判断能额外拦住的可达路径 | 返回值或拒绝结果如何影响实际操作 | 移除本项会失败什么 |
| --- | --- | --- | --- | --- |
| 来自用户/需求的行为增量 | 指明调用者、前置条件及实际建立顺序 | 用当前代码证明上游未覆盖，或标“未找到/证据不足” | 调用方是否读取结果、是否仍执行后续副作用 | 绑定用户结果或独立边界合同，不用新增测试自证 |

1. **先保留既有行为边界。** 同一输入的不同消费者可以有不同门槛；逐项列出事件/操作自己的资格，不因共用 action、helper 或来源就统一加载、身份、时机。例如首次点击可不依赖加载成功，播放已有加载门槛；扩展可触发动作不自动授权修改二者的加载合同。
2. **追到现有调用链。** 核对成功状态由谁创建、何时确认、失败时是否已返回/暂存、所有生产调用方能否绕过该路径。缺少实际可达的绕过入口时，不把“直接调用底层方法可能出错”写成当前生产缺陷或必要接线；查不全时标证据不足。直接调用测试不等于生产入口。
3. **判断保护实际控制什么。** 区分拒绝业务操作、跳过一次账本写入与仅返回状态。若调用方忽略返回值并继续上报，不得宣称该判断给上报增加了资格门槛；检查内存与持久化是否反而形成不同条件。
4. **分开必要接线与额外防御。** 已有门槛覆盖全部当前生产路径时，新增二次判断按重复保护审查；当前目标未要求独立加强底层 API 时，不纳入最小必要集合。若存在真实信任边界、明确的公开 API 防御合同或已证实的绕过路径，再按独立依据判断，不能机械删除安全校验。
5. **替代或撤回后再收口。** 消费者被删除、恢复旧实现或不再读取新字段后，重新追踪新增 helper、export、类型放宽、mock 与专属断言。没有剩余生产/契约贡献时，撤回该支撑及只为它成立的测试；原有业务回归保持。只读审查仅建议，用户批准后才修改。
6. **对相邻扩张使用同一反事实。** 纯改名、条件补强、异常兜底、跨端同步和新状态都分别回答“保持原行为能否满足本次目标”。能满足但解决另一目标的，单列范围外；理论上更稳健、同目录已有类似写法、测试通过均不是必要性依据。不得由一个重复判断外推整条链路或全仓都应清理。

### 名称同步的误判反例

[RR07：实例键改名](../../memory.md#rr07)提示：当旧字符串已能区分实例、业务身份另有 owner 时，“命名统一”本身没有证明移除此行会破坏当前目标。沿用本文件既有反事实规则，分别判断同文件中的功能修复与名称整理，不因文件整体必要而给所有 hunk 背书；该案例不授权自动回退或全仓改名清理。
