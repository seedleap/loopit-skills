# 人工结论与完整AI复核

本合同维护报告的阅读决策，不改变全量审查要求。先完成全部冻结非测试文件/hunk的实质判断，再组织人工前层；结构覆盖、代码块数量或绿色测试不能证明语义正确。适用案例与替代关系见[统一案例库](../memory.md)，只读取本次命中的标签。

## 人先看什么

1. 用紧凑概览和一句结论明确对象，按真实业务主线交代改前/改后、测试操作、通过标准及已有证据。单一明确改动不用硬凑三条；确认缺陷不能代替完整分支说明。
2. 用 ✅/❌/⚠️ 加文字标明对象、版本、确认层级和行动。✅ 可为代码/测试/独立人审中的具体一层；❌ 注明缺陷发生版本；⚠️ 区分执行方缺证据与用户需决定的业务取舍。可查技术事实由执行方核实，已确认事项不重复要求用户判断。
3. 确认问题在前层独立主卡展示，先于长diff；同项只维护一份主说明，不再另设“重点与争议”重复其内容。问题按严重度优先，同级参考危险系数，无问题不凑空区。
4. 高关注通过项也给短结论：启动/公共埋点、测量反馈、静态映射/名单、公共代码大块修改等命中实际风险时，主动说明为何改、原行为和副作用边界。判断方法由[file-change-review](file-change-review/impact-and-evidence.md#high-attention-changes)维护；不把风险信号写成已确认缺陷，也不把所有技术细节铺成人工检查清单。
5. 读者能直接回答“是否要看、关注什么、谁做下一步、是否需我决定”。仅有资料汇总或测试总数不够；没有新增人工动作时明确说明。

## 关键原因旁的证据

- 关键源码图、真实行号/版本及其证明什么直接放在同一问题的原因旁；默认显示最小关键证据，完整代码、diff与复现细节可折叠。使用[plain-language](plain-language.md)现有标注规范，不另建重复页面。
- 截图来自真实源码或真实运行，标清来源；源码高亮图标“非diff”，不能冒充新增/删除。没有可靠证据则说明缺口，不编造图。
- 修复继续按入口的双基线规则保留原问题、发生版本、修复状态和两份完整业务diff。字段疑问使用已有字段语义owner，不凭名字猜值/实验分组。
- 同一代码的源码、patch、截图不是三份独立验证；侧会话转述也不自动增加证据强度。证据边界紧邻相关断言，不恢复独立验证汇总。

## AI复核层保留什么

完整层默认收起，标「🤖 给 AI 二次复核 · 人工按需查证」；人工通常不必逐项读。AI任务是逐块核对需求关联、独立必要性、原行为、消费者、反例和证据，不能只复述已有判断。

保持 `修复/需求关系 → 冻结提交阶段 → 文件 → hunk及就近分析`、风险排序、必要性、最小性、完整原始patch、真实行号、证据锚点。所有未入选前层的非测试记录仍能访问；测试仅独立行数统计，不展示源码或评价。折叠只改变注意力分配，不减少覆盖，不恢复已删除的过程总述或验证总表。

关系标题只在所属关系内吸顶，下层文件头按关系头实际高度避让；下一关系自然替换，代码锚点避开两层标题，不累积悬挂旧标题。

## 输入与交接

- 继续用非空 `focus_review_html` 写人工分支说明、关注项和行动，不复制已由 `issues` 维护的问题长卡；生成器不从分数、文件名或commit标题猜业务结论。旧输入可省略该字段。
- `issues` 主卡默认位于完整折叠层之外。可选 `issue.inline_evidence_html` 在关键原因旁插入最小静态证据；旧 `issue_evidence_html` 保留。片段只允许安全文本/链接及内嵌PNG/JPEG，不允许自动网络资源、SVG或执行内容，见[数据合同](report-data.md)。
- 所有引用精确绑定冻结ID/阶段身份。定位会打开祖先折叠，交付前核对锚点，不跨版本借用同名ID。
- 侧会话按同一问题/关注点去重承接：记对象/基线、用户认可范围、执行证据、报告落点和实际完成阶段。只有投递或写入goodcase时写“已登记，正文待补”；完成原报告回填后才能写正文已更新，外部同步另记。不默认创建侧会话或把局部认可扩大为整分支放行。
- 用户要求飞书报告或同步时再读取[飞书交接参考](feishu-review-handoff.md)，不因审查报告本身自动发送。

## 验证与复用

校验人工层不重复主卡、结论与动作可直接读；确认问题和关键证据不藏在全量折叠内；完整文件/hunk、patch和行号集合不变。检查离线、静态片段安全、自动展开、吸顶接替及窄屏。

本次样板支持用户偏好和情境启发式；模拟新情境只验证方法能否产生具体动作，真实减少纠偏/副作用仍待后续独立任务回填。
