# 字段与改名判断的证据核验

用于核验“这个参数相当于另一个字段改名”“保留旧名字是否意味着逻辑没变”“绿色代码是否整段新增”等具体说法。它补充 judgment-analysis 的取证选择；简单事实问答不机械生成全套表格，不增加业务修改、测试或设备操作授权。

本方法从字段语义与双基线审查实践提炼，适用边界见[案例 RR09–RR10](../memory.md#rr09)。它是有条件的启发式，不能代替当前项目证据。项目字段的当前含义以项目 owner 和实际实现为准，不把本案例取值固化为跨项目字典。

## 从疑问到可验证结论

1. **拆断言。** 将一句包含多个概念的说法拆为 1–3 个可证伪命题。分别判断“名字是否保留”“字段是否同义”“行为是否仅重命名”；允许部分成立，不让一个正确分句替另一个分句背书。
2. **冻结比较对象。** 记录 checkout、HEAD、dirty 与实际 base/target。修复前后变化和相对目标分支的累计变化分别核对；用文件内容身份和真实 patch 判断二者是否相同，不能凭截图外观判断。后续 HEAD 只证明当前状态，不倒改历史证据；未检查远端不称“最新”。
3. **分清语义。** 对会影响判断的字段列最小映射：`字段 key → 实际值及类型 → 业务职责 → 创建/维护 owner → 消费者`。区分本地变量名、序列化参数名、协议/埋点属性名和业务 ID 值。字段名相似不证明同义，保留 wire key 不等于保留旧页面身份；字段值变化也不自动证明整个流程新增。
4. **闭合数据流。** 回读生产者写入条件、导航/DTO/mapper 的转换、消费者分支和最终输出，引用真实文件、行号及版本。特别核对字符串与布尔值、缺省值、优先级与覆盖；生产者赋值不能代替“消费者实际使用”的证据。
5. **找能推翻结论的反例。** 检查同一业务 ID 在旧/新入口共用、标记缺失或显式 false、不同参数形态等真实可达情况。已有覆盖可复用；只有与断言直接相关且已授权时才追加最小验证。隔离 helper 或 mock 的成功不能证明真实入口、跨端或后台收件。
6. **逐断言收口。** 每条结论就近给支持/反驳证据、成立条件与未验证层级。已核实的字段事实不交给用户猜；只有业务口径或兼容取舍需要用户选择。需要额外实现或操作时停在已有授权边界。

## 置信度与证据来源

- 代码链闭合可写“代码层已确认”；直接相关测试可写“指定场景回归通过”；设备、网络/后台和实际影响占比各按自己的证据标记。置信度属于具体断言及层级，不给整份报告笼统贴“高置信”。
- 同一份源码的引用、Git diff 和源码截图是不同呈现，不能计成三份独立验证。多个说明都转述同一测试日志，也不增加独立证据数。
- 没有测量或校准方法时不编造置信百分比；代码证据充分也不能写成设备必现、双端通过或后台已收件。反证或版本漂移出现时重新判断，不靠增加截图维持原结论。
- 证据不足时，明确缺的是字段 owner、真实消费者、运行条件还是后端回执，并给最小补证动作；不为填表编造复现路径或新问题。

## 报告如何承接

报告中只展示本项的可核对解释：用户疑问、逐断言结论、必要字段映射、生产者到消费者的证据和置信边界。已有问题卡内追加，不另铺方法论总述或独立验证汇总。比较基线、完整 diff、历史 P? 与修复状态的呈现由 [review-report](../SKILL.md) 维护；截图标注和用户表达由 [plain-language](plain-language.md) 维护。

## 反例与停止条件

- 若真实实现仅将本地标识符改名，wire key、值、条件和消费者均保持，可得“内部重命名”的结论；不能预设所有改名都有业务变化。
- 若某字段确实改变身份选择或门槛，按新增/改变的行为说明，不能因为字段名未改就归为纯改名。
- 若只能找到一个写入方、消费者未知，保留“证据不足”；不能直接判死字段、建议删除或扩大扫描整个项目。
- 只问字段含义时核对当前链路即可；用户关心新增逻辑或修复差异时再核对相应双基线，不把所有问答升级为分支审查。
