# Loopit Tracking Acceptance

按已确认埋点方案和真实场景验收 Loopit 采集链路。默认只读核对和输出证据，不修改业务代码、不写 TE 元数据、不把静态检查结果当作线上通过。

## 工作流程

1. **冻结验收范围。** 记录目标版本、环境、平台、账号、作品、时间窗、时区、场景和预期事件。逐场景列出触发次数、必要字段、关联键、去重规则以及成功、取消、处理中、未知和失败的预期。
2. **核对实现。** 回读代码触发点、字段来源、转换和发送路径，区分源码事实、静态检查和运行观察。方案与实现不一致时记录差异，不用实现反推方案已获批准。
3. **执行场景。** 按真实用户路径执行最小覆盖，检查可见、点击、提交、返回、重进、重复操作、失败恢复和异步结果。需要设备时遵循当前设备授权和静音约定，保留场景截图或录屏证据。
4. **对账载荷和收件。** 分别核对客户端最终 payload、TEA 服务收件和权威业务终态。按事件 ID 明细核查漏报和重复，只有聚合次数时只能给出聚合结论，不能声称逐条收件。
5. **输出验收矩阵。** 每个场景给出通过、失败、阻塞或未验证状态，绑定预期次数、实际次数、关键字段、归因键、证据位置和缺口负责人。涉及交付、入账等业务成功指标时，缺少权威终态则相应成功结论和转化率留空。普通点击、曝光或页面到达按方案中的观察目标验收。

## 关键判断

- 页面到达、实际可见、点击、请求成功和业务终态分别验收。
- SDK 回调、请求成功和服务端确认属于不同证据层级。
- 重试、回放、查单和恢复不能自动计为新的业务提交。
- `event_id`、队列持久化或 SDK 接收不能单独证明业务 exactly once。
- 账号、作品、订单和时序只能支持相应粒度的聚合分析。逐次归因需要已核实的会话键或订单键。
- 目标版本、环境、筛选条件和时区必须随 TEA 对账记录，避免跨环境或跨版本串证据。
