# Loopit Tracking Implementation

将已确认的 Loopit 埋点方案落到实际代码链路。先遵循目标仓库的适用规则，按用户授权范围修改代码，TE 共享元数据和生产配置按各自授权处理。

## 工作流程

1. **确认输入契约。** 读取已确认的埋点方案或机器可读契约，确认目标事件、属性、页面、触发时机、条件必填和成功/失败边界。方案缺少关键口径时先标记缺口，不自行改变统计定义。
2. **核对代码环境。** 确认目标仓库、当前分支、HEAD、适用 `AGENTS.md` 和工作区改动。沿真实链路定位动作入口、上下文 owner、字段转换、消费者、发送器和最终 payload，不以出现 `track()` 作为完成证据。
3. **复用既有采集能力。** 优先复用现有 analytics client、事件常量、属性映射、身份和去重机制。实现新增事件或属性时保持方案中的语义、类型、枚举、实体绑定和 `page_id`，不因代码方便创建同义字段。
4. **处理异步和结果边界。** 区分点击、请求成功、SDK 回调、服务端确认、处理中、取消、未知和确定失败。需要跨页或恢复归因时冻结原始账号、作品、页面和业务关联键，不能从后续当前上下文补造原始归因。
5. **完成局部验证。** 运行与改动直接相关的静态检查、类型检查、单测或现有回归。必要时输出逻辑字段到最终出网字段的映射，区分源码事实、静态结果、运行载荷和 TEA 收件。
6. **交付实现记录。** 说明改动文件、事件触发点、字段来源、保留的旧行为、验证命令和未验证项。用户未明确要求时，不执行 TE 元数据写入、提交、推送或发布。

## 约束

- 修改前保护用户已有 dirty 工作区，避免格式化和无关重构。
- 事件名、属性名、类型和枚举以已确认方案为准。区分本次要修正的实现差异与需要产品决策的口径冲突，已获授权的实现差异直接修正，口径冲突先澄清。
- 原账号归因、传输身份和 SDK 当前登录身份分别核实。保存原 uid 不授权把 SDK 切回旧账号补发。跨版本迁移字段时检查旧数据、旧客户端、报表依赖与切换条件。
- 不把本地构建成功、SDK 接收或请求发出当作 TEA 收件证据。
- 不自动补全 trace、订单键或全量上下文。只有指标确实需要且方案已确认时才接入。
- 参考现有链路时读取 [rn-analytics.md](references/rn-analytics.md)。输出字段映射和验证状态时使用 [implementation-checklist.md](references/implementation-checklist.md)。
