# 数据与命令合同

填审查数据或适配已有报告时读取。本包两步脚本只执行 Git 读取与 JSON → HTML 转换；人工/Agent 完成语义判断。

## 范围与统计

页首将统计摘要与基线/目标合并为紧凑概览，默认只展示当前分支、目标分支、commit 数、`+新增 / -删除` 行数。非分支 scope 使用真实对象名称；缺少可靠 commit 数时明确未知或不适用，不从文件数推算。增删行保持对应冻结范围的原口径，不将 hunk 数或增删行配对臆算为“修改行数”。

测试默认跳过审查，仅记录文件路径及新增、删除行数与合计；不读源码、不填审查字段、不评分、不嵌入测试 diff。非测试文件以明确路径生成快照，测试另用同基线、同范围的 `git diff --numstat` 保存到独立统计数据，并在 `focus_review_html` 的紧凑区域展示；业务审查统计与测试行数分开。未跟踪测试文件按真实新增行数计，二进制标未知。下文完整快照、逐块、关系覆盖及评分要求只适用于纳入审查的文件；用户明确指定审查的测试除外。

以下纳入审查范围的完整快照与审查字段继续保留。路径、完整 SHA、共同祖先、range 说明、采集时间/指纹、本地三层状态和详细统计默认折叠或放在其所属文件区域；页首精简不改变快照或审计信息。多提交另按下文提供 `change_relations`，关系/阶段组合的报告也遵守同一概览统计口径。

页面不另建“先辨清两种差异”过程说明，也不在关系主视图之外重复生成“后续修复／撤回关系”或“提交演变”总表。`change_relations` 主条目及其直接展开的代码必须保留；差异归属、后续修复与当前状态贴近对应阶段、文件或问题呈现，不借 `sections` 重复总表。这不改变既有强制语义审查表。

页面不提供路径/旧路径、文件类型、关联问题等文件筛选，也不显示筛选结果计数或“无匹配”状态。各范围文件按业务/辅助/测试区域完整列出；展开/收起、代码换行、证据跳转仍可使用。文件类别、问题关联等内部字段继续保留，供分区、统计和证据定位使用，不因移除筛选而删数据。

| scope | 改前 | 改后 | untracked |
| --- | --- | --- | --- |
| worktree（默认） | base，默认 HEAD | 当前磁盘 | 纳入 |
| staged | base，默认 HEAD | Git index | 不纳入 |
| unstaged | Git index | 当前磁盘 | 不纳入 |
| range | 指定 base commit | 指定 target commit | 不纳入 |

`--base` 解析为真实 commit；unstaged 的实际 base 固定是 index，不接受自定义 base。`--target` 仅 range 使用。`--path` 为仓库相对 literal pathspec，可重复；`--exclude` 为 Python fnmatch 路径模式，可重复，排除路径和模式进入快照。不要用 shell 通配展开代替这两个参数。

新增文件改前行数 0，删除文件改后行数 0；未跟踪文件相对空文件生成 diff。有无末尾换行均按文件真实行数计，缺末尾换行保留 marker。rename 保留旧路径；仅 mode 修改无 hunk，但显示完整元信息。二进制 patch 不嵌入二进制 payload，行数和增删为 null，页面显示未知并声明边界。

`layers` 是采集时三层文件清单，不代表 range 纳入了本地改动。staged/unstaged 同文件最终 aggregate patch 可能抵消；范围由 `scope/base/target` 决定。跨范围复用指纹或审查解释不合法。

## snapshot.json

由 `collect_diff.py` 生成，**不要手动改源码、行号、统计或指纹**。

```json
{
  "version": 1,
  "repo": "/actual/repo",
  "branch": "branch",
  "head": "full commit hash",
    "base": "resolved commit hash / index (unstaged)",
  "target": "worktree / index / resolved commit hash",
  "scope": "worktree",
  "captured_at": "UTC ISO time",
  "fingerprint": "SHA256 of canonical snapshot excluding timestamp and fingerprint",
  "files": [{
    "id": "F001", "path": "src/file.ts", "old_path": null,
    "status": "modified", "bucket": "业务", "category_basis": "路径分类规则；待人工核对",
    "before_lines": 100, "after_lines": 101, "added": 2, "removed": 1,
    "binary": false, "patch": "complete unified diff",
    "hunks": [{"id": "F001-H01", "header": "@@ -1,3 +1,4 @@", "lines": [" context", "-old", "+new"]}]
  }]
}
```

文件类别固定 `业务/测试/配置/文档/生成物/其他`。状态包括 modified/added/deleted/renamed/binary/mode-only。`hunk.lines` 含原 prefix，**不含 @@ header**。指纹包含完整 patch 与内容 SHA，空 diff 也明确展示。

## review.json

采集器生成空表；从实际审查填非空字段。字段值均为普通字符串，HTML/Markdown 不执行。`snapshot_fingerprint` 必须与 snapshot 完全一致。语义内容不能用“已检查”“测试绿”代替。

顶层：`version=1`、`snapshot_fingerprint`、`title`、`goal`（非空字符串数组，兼容旧版单目标字符串）、`non_goals` 字符串数组、`summary` 整体判断、`files`、`issues`、`sections`、`validations`。

`goal` 每个数组元素只写一个独立目标；有多个时，页面按 1、2、3 编号逐项换行，不能用分号拼成一段。单个目标直接显示，不强制编号。新模板为 `goal: []`，正式报告须填至少一个非空目标；草稿显示待填写。旧版单目标字符串仍可渲染，多目标长段应由审查者依据真实含义拆成数组，不自动按标点切分。

```json
"goal": [
  "保持 leaprn 开屏站内跳转染色。",
  "保持 edit_profile 服务端标识及头像框弹窗入口。",
  "保护同页新消息只打开、不预选、不自动佩戴的行为。"
]
```

`files` 用 file ID 做 key，每个文件：

| 字段 | 含义 |
| --- | --- |
| bucket/category_basis | 可选：人工修正分类与依据 |
| purpose | 文件用途/改前职责 |
| change | 先用用户入口、操作与可观察结果说明改动用途；稳定符号放 position 或后续机制/证据中，不用调用顺序代替用户场景 |
| position | 可选：单独填写方法/组件/稳定符号；未填写以 change 的稳定符号说明为准，不用 @@ 代替 |
| why | 对应独立目标与必须改变已有功能的原因 |
| without | 保留其他改动而移除此文件变化，会失去什么 |
| necessity | 必要/有条件必要/冗余/过度改动/证据不足 |
| reasonableness | 合理性、owner/边界/消费者与最小充分依据 |
| loss | 否/是（按需求移除）/是（移除意图待确认）/是（非预期丢失）/高疑似/证据不足/不适用（新增文件） |
| risk | 展示摘要：没有需提示的风险或影响判断的证据缺口时仅填 `无`；其余用一句精简说明点明 P?、风险或实际缺口，不重复历史过程 |
| risk_detail | 可选：内部保存完整风险判断、验证依据与边界，不在文件风险摘要重新展开 |
| risks | 可选：未包含在 issues 的逐条证据缺口或补充说明，单独编号；不要重复已有 P?。可独立修正/复现的问题应进入 issues，risk 保留总体边界 |
| pair | 原生文件双端判断的展示摘要：确认一致时仅填 `一致`；不一致、平台差异或证据不足时，填结论及一句精简说明 |
| pair_detail | 可选：内部保存另一端文件、稳定符号、正常/异常分支和完整判断依据，不在文件双端摘要重新展开 |
| hunks | 每个 hunk ID 的分段解释 |

### 全量审查后的人工阅读区

新报告完整审查字段和覆盖校验通过后，人工填写可选 `focus_review_html`，按[人工结论与完整AI复核合同](focus-review.md)说明业务主线、前后差异、测试/通过标准、高关注结论与读者动作，不复制 `issues` 主卡。非空字符串经静态清洗后置于结论下；确认问题主卡位于默认收起的 `full-review` 之外，完整非测试判断、阶段、文件和diff仍保留在其中。旧输入省略时兼容，空值/非字符串拒绝。可选 `issue.inline_evidence_html` 为非空字符串，在该问题关键原因旁插入最小证据；旧顶层 `issue_evidence_html` 保留。片段支持安全文本/链接、figure/figcaption和仅data URL的PNG/JPEG（base64及文件签名须有效），拒绝外部图、SVG、脚本、事件属性及任意style；CSP继续禁止自动外网资源。生成器不推断证据来源/语义，提交者须标真实版本、文件/行号和证明什么；不提供虚假截图补字段。不新增必填字段，不据摘要减少逐项输入或宣称语义已验证。 `issue.inline_evidence_html` 中的 `id` 与 `#` 锚点按问题所在阶段统一加前缀：写 `proof-P1`、`#hunk-F001-H01`，渲染为 `final-proof-P1`、`#final-hunk-F001-H01` 或对应历史阶段前缀；不要预写 `final-`。顶层 `focus_review_html` 与旧 `issue_evidence_html` 不做阶段命名空间改写，须填写最终目标 ID。

### 文件层风险与双端判断的简短展示

`risk`、`pair` 由审查者按证据填写短结论，生成器原样展示，不从“未发现确认问题”、测试通过或另一端文件存在自动推断。正常例为 `risk: "无"`、`pair: "一致"`；异常例为 `risk: "待确认：尚未覆盖后台切回时的重复上报。"`、`pair: "不一致（P1）：Android 缺少取消后的会话失效保护。"`。无另一端同构能力或存在合理平台差异时沿用真实结论并简述，不强填“一致”。

完整审查依据可存入 `risk_detail`、`pair_detail`，原始证据及 P? 继续保留；这两个内部扩展字段不进入可见文件说明，不另造长表。通用的“未做本阶段复跑”等过程说明不反复铺在每个文件；确实影响本文件判断的未验证条件必须保留在短摘要中，不能为了显示“无/一致”隐去真实缺口。已有长文本不由渲染器机械截断或降格成正常结论。

### 文件层需求摘要与最小必要改动

新填写的每个文件增加两个对象，原 `change/why/without` 继续保留作折叠补充与审查依据，不再在文件主说明中并列铺开：

```json
"requirement_context": {
  "description": "用户在作品里拖动、滚动等真实操作也能计入首次播放。",
  "source": "实际需求文档路径或链接及章节；缺失时明确写未取得需求文档",
  "coverage": "明确要求",
  "rationale": ""
},
"minimum_change": {
  "verdict": "符合",
  "reason": "沿现有采集与上报链增加必要接线，没有修改无关业务流程。"
}
```

- `description` 为人工提炼的一两句需求描述，不能串联所有代码块的技术机制。默认显示标题“需求文档中需求描述”，来源及原三项完整说明位于默认折叠的“展开补充说明”。
- `coverage` 固定为 `明确要求/必要支撑/需求未要求/需求依据缺失`。`description/source/coverage` 必须非空；未取得文档时明确标缺失，commit 正文仅能作为目标补充，不能称为需求原文。
- `coverage` 非“明确要求”时，`rationale` 必须非空并在折叠区之外可见，说明与目标的因果关系、为何不能省略及最小收口建议；不能只写“合理”或引用测试通过。明确要求也可补充合理性。
- “是否符合最小必要改动”作为独立可见项，`verdict` 固定为 `符合/部分符合/不符合/证据不足`，`reason` 非空。包括必要支撑和验证的最小完整集合，不能从 `necessity`、风险分或测试结果自动推导。
- 旧输入同时缺少两对象时保持兼容，但明确显示需求/最小性证据不足，不自动补造结论；新模板包含两对象，正式输入如提供其中任一对象则必须完整填写两者。草稿可留空，不能以草稿交付。
- 本次合并针对文件层说明；每个独立 hunk 的必要性、合理性和反事实继续就近保留，不删除完整 diff 或语义审查表。默认跳过的测试只记录行数，不填写这些审查字段。

### 业务与测试的展示规则

审查快照仅纳入非测试文件，正式完整性校验仍覆盖快照内全部文件和块。测试行数单独记录、分区展示，不为通过生成器校验而伪造测试审查。现有渲染器的测试摘要/完整 diff 属兼容能力，默认不使用；仅当用户明确要求审查指定测试时才纳入。

这些区域仅在当前范围有实际差异文件时展示。无差异文件的区域不输出标题、零值统计、解释、空态提示或导航；有测试 diff 则继续展示路径与增删行数清单，并标明跳过审查，不提供源码入口。依据快照中的真实差异判空，rename/mode-only/binary等元信息变更即使文本hunk为0也不是空区；不修改内部分类、文件覆盖或指纹。

业务与辅助文件保留完整审查呈现。测试仅统计路径、新增及删除行数和合计，不填写 `change/risk/hunks` 等审查字段，也不描述覆盖内容。已取得的实际执行结果可留在内部 `validations` 并就近说明业务证据，不因跳过测试审查自动运行测试，不从行数或测试名推断通过。

每个 hunk：`title`、`change`、`necessity`（同固定枚举）、`reasonableness`、`without`、`evidence` 均非空，`issues` 为可选 P? 数组。`evidence` 指真实行号/符号与能证明什么；该 hunk ID 是代码证据锚点，问题可直接关联。必要性与合理性是不同判断，不互相替代。

代码块标题始终显示 `必要性：<necessity>`，不是仅在展开后的说明里显示。`冗余/过度改动` 是人工确认的非必要结论：渲染器给该块增加 `data-necessity`，标题及审查信息区使用黄色背景，并显示 `⚠️ 非必要`；原始 patch、代码行增删红绿与关键链路红字不变。`必要/有条件必要/证据不足` 不自动套用非必要黄底，不能把未证实的条件或疑似问题包装为确认结论，也不能由文件结论连带标记其全部 hunk。

新增防御或资格判断的 `reasonableness/evidence` 应说明当前生产调用者、既有门槛 owner、建立顺序、额外可达路径及返回值的实际消费；`without` 说明保留其他改动而移除本块会失败什么。执行 [已有门槛审查](file-change-review/scope-and-necessity.md#已有门槛与防御改动)；仅直接调用底层方法的测试不证明生产绕过路径，撤回消费者后重新核对专属支撑。无依据写证据不足，不由生成器推断业务必要性。

`title` 和 `change` 先从用户视角回答“在哪个页面、做什么、看到什么变化”。例如 Get Frames 的退出后导航块，应写“用户在没有可用头像框时点击 Get Frames，面板先收起，再打开配置的获取页面”，而不是只写“finishExit 先 dismiss、清空 ref，再 router.push”。后者属于实现机制/代码证据。支撑块关联同一真实用户场景；无直接用户变化时说明内部支撑和原表现保持。未执行设备验证时，只能说明源码支持的结果/顺序，不能据此宣称动画已顺畅或已消除闪屏。

涉及登录、首页 Feed、埋点等关键执行链的改动，对应文件标题与命中 hunk 标题标红，并带 `‼️ 改动 xxx 关键链路，仔细审查` 的具体链路名称。文件聚合所涉链路，混合文件未命中的 hunk 不连带标红；折叠时仍展示预警、用户场景和行数。依据实际变更与调用链识别，不按路径名/上下文关键词自动推断；在该文件或块的审查依据中简要说明触达点。多链路需分别点明，关键链路 `‼️` 与大段修改 `⚠️` 可同时出现，均不等于确认 finding。此呈现规则不修改 patch、行号或指纹，不增加必填数据字段。

独立 hunk/职责段若被审查判为冗余、过度设计或额外重构扩大范围，标题直接展示对应高亮标签，折叠状态也保留；不能仅靠 `necessity` 字段藏在正文。标签沿用真实判断及确认度：`冗余`、`过度设计`、`额外重构扩大范围`，或带限定语的 `疑似过度设计`、`范围必要性待确认`。现有必要性枚举不变：过度设计/范围扩张按实际对应 `过度改动`，无法确认时为 `证据不足`，不新增枚举或必填字段。`reasonableness`/`without`/`evidence` 说明目标、反事实和依据，并给最小收口建议；混合文件只标命中块，不从全文件结论机械复制标签。

### 公共/私有作用域标识

文件标题区域在所属文件diff滚动期间吸顶；至少能识别具体文件及其公共/私有、危险系数等审查信息。切换文件时替换吸顶身份，不将多个历史文件头持续堆叠；锚点定位需要避开吸顶遮挡。此处是展示要求，不修改冻结字段或源码。

文件与方法/函数分别识别作用域，并在标题显示文字标签，折叠状态也保留。文件用 `公共文件` / `私有文件` / `范围待确认`；方法或包含方法的块用 `公共方法` / `私有方法` / `公共/私有方法混合` / `范围待确认`。非方法的配置、类型或顶层接线注明实际作用域，不伪装成方法。

公共/私有以当前审查的代码边界为参照：记录 public API/导出与可见性、真实直接调用者及公共入口的间接传播。模块内部为跨文件接线而 export，不自动是对外公共API；对外公开但当前只有一个消费者，也不能仅按调用者数量标私有。无命中调用者不等于已经证明私有。文件标签不能覆盖全部方法：公共组件文件的局部函数可私有；其改动仍可能经组件影响多页。混合块逐方法注明，必要时在保持原patch的说明中分段。

每项用一句说明“共享给谁/局限于哪里”，将实际影响面纳入危险系数；私有仅说明可见性/调用边界，不抵消关键链路或已有功能风险。结构化制作可在文件和hunk中分别补充可选 `scope_assessment`，记录 `classification`、审查边界、涉及符号、直接消费者、间接影响及依据；不修改冻结快照/指纹，不要求为旧数据补造作用域结论。

### 文件与代码块危险系数

新报告的每个文件和hunk/独立职责段均按 [危险系数评分规则](risk-scoring.md) 评估，并在标题显示0–100分、文字等级及绿/黄/橙/红颜色。得分依据不能只写行数；要覆盖业务影响、公共复用、既有功能回归、复杂度、相对规模、验证缺口。文件至少取最高块风险，不平均；小改动的关键链路/公共契约应用升级下限。未知维度保留区间和缺口，不能伪造精确低分。

文件显示顺序按文件最终危险系数降序；文件内部hunk/职责段也按各自危险系数降序。分组报告在各明确范围内排序，同分稳定保留原顺序，区间按上界且保留待确认；无评分不当低分。不得为排序重采或改写patch/hunk数组及指纹；从冻结数据创建展示顺序，原始patch的复制/下载仍保持源码顺序和完整内容。显示编号可以随呈现顺序变化，但稳定hunk ID、旧/新行号和证据引用不能改变。

结构化制作可在 `files.<文件ID>` 与其 `hunks.<块ID>` 各自增加可选 `risk_assessment` 对象，包含 `model_version`、`score`（0–100整数；未知时为null）、`score_range`（未知时的上下界）、`level`、`confidence`、`reason`、六维 `dimensions`（名称/权重/0–4等级或未知/理由/来源）、适用升级下限及其依据；文件注明最高块分和整体影响的汇总。全部内容是审查者基于事实的判断，不由采集器从路径/行数自动判定。旧数据无需补造数值，新报告不能用旧数据缺字段为由跳过用户要求的评分；不改变快照、指纹、现有必要性枚举或把评分当issue严重度。采用不支持扩展对象的制作路径时，仍须在标题和现有说明中完整呈现评分/依据，不得静默丢失。

展示 hunk 标题时，在标题旁直接显示该块 `+新增 / -删除 行`，折叠状态也保留。数值从冻结的 `hunk.lines` 中按 `+`/`-` 前缀计算；上下文、`@@` header、patch 元信息和缺末尾换行 marker 不计入。需要总改动数时为新增与删除之和，不从旧/新范围长度推算。大段新增、删除或重写的块在同一标题加 `⚠️ 大段改动`，保留实际行数；预警不等同缺陷确认或优先级。此为呈现约束，不改原 patch、行号或指纹，也不增加必填数据字段；未获用户明确阈值时，不将自选数值记作用户规则。

问题的关键代码用可选 `focus` 选择真实行，而不是只给整块红绿颜色：

```json
"focus": [{ "side": "new", "line": 42, "marker": 1, "explanation": "E1：这一行把状态放到共享 owner，支持 P1；不证明设备表现" }]
```

side 为 `old/new`，line 为该 hunk 确实包含的正整数行号，marker 为块内唯一正整数。删除行用 old，新增行用 new，上下文可选任一侧；每个标记写“该行证明什么”并关联 E?/P?。渲染器校验坐标，显示聚焦边框/背景、数字标记和邻近解释；不改原始 patch 或行号。无关键证据点可留空，不能假造坐标。

每个 issue：

```json
{
  "id": "P1", "priority": "P1", "title": "用户能看懂的问题标题",
  "evidence": "代码实锤", "frequency": "频率待确认",
  "locations": [{"file_id": "F001", "line": 42, "symbol": "actualSymbol"}],
  "condition": "页面入口、触发条件与关键原因",
  "user_problem": "用户在哪里、做什么、看到什么异常；未运行标代码推导",
  "reason": "理解问题必需的关键原因，保留证据边界",
  "evidence_refs": ["E1", "F001-H01"],
  "invariant": "破坏的契约/不变量，关联代码证据 ID",
  "impact": "用户实际或可能观察到什么", "scope": "用户、平台与版本范围",
  "recovery": "是否恢复以及条件",
  "repro": {
    "persona": "用户画像", "preconditions": "版本/数据/页面条件",
    "steps": ["打开具体页面", "执行可观察的用户动作"],
    "actual": "已观察结果；未运行必须标按代码推导",
    "expected": "来自需求/契约的预期", "observations": ["页面状态或日志观察点"],
    "type": "候选复现路径/待验证", "status": "未执行",
    "boundary": "以下为代码推演路径，设备运行态未验证"
  },
  "suggestion": "最小修正或补证据动作"
}
```

证据等级固定 `运行实锤/测试实锤/代码实锤/高疑似/猜测/待确认`；频率固定 `稳定复现/偶现/频率待确认`。priority 为 P0/P1/P2/P3，与唯一 issue ID 分开。`repro.type` 为 `已执行` 或 `候选复现路径/待验证`；稳定测试不自动成为真实用户稳定复现。

已确认问题主卡接在页首结论与业务主线之后，位于完整审查折叠层之外，先于 commit/文件 diff 与长审查表，按严重度优先、同级参考危险系数；保留证据等级及运行验证状态，不把疑似项变成确认项。无确认问题时不生成空问题区。设备或模拟器验证以使用者当次指令或当前项目合同授权为前提，再核对空闲及代码身份匹配；证据记录平台/版本、操作条件、实际结果及截图/日志等引用。无授权时保留缺口并继续静态审查。未复现只覆盖已执行条件；占用、驱动失败或版本不匹配属于受阻/未验证，不能冒充未复现。

问题必须依 `plain-language` 填用户化表现与步骤。受控测试输入/方法调用写证据，不伪装成设备操作。location 行号为真实当前行号，删除行标明基线；无法定位不猜测，line=null 并说明缺口。源码关键行证据可以使用同 hunk 的 `issues` 字段绑定 P?。

`user_problem`、`reason`、`evidence_refs` 是问题说明的可选显式字段；首次填写推荐提供，旧数据未提供时分别使用 repro.actual、condition，并保留 hunk 关联。E?/F?-H? 必须指向实际证据和对应解释，不凭空生成编号。

## sections：语义审查表

新版渲染入口为 `scripts/render_compact_report.py`，要求全部文件/块提供 `risk_assessment` 与 `scope_assessment.reason`。可选 `target_label` 为页首目标名称；分支使用 `--commits manifest.json` 按冻结顺序加载，每项 `key/commit/subject/snapshot/review`，文件路径相对 manifest，`inventory` 可保留 merge 继承路径清单。主视图由下述 `change_relations` 组织，不再由 `follow_up` 文本加独立 commit 代码列表代替。多个关系/阶段的 ID 加各自前缀，原快照与下载 patch 不变。附加 `risk_method_html`、`issue_evidence_html` 仅供本地制作的静态说明，经标签/属性白名单清理，不允许脚本、事件属性或自动加载外部资源。

### 修复需求关系与就近代码演变

分支多提交报告的总 `review.json` 必须提供非空 `change_relations`。每条是人工审查确认的需求或修复主题，直接在其下按实际提交顺序展开代码；不能按 commit 数硬凑相同数量的 R 条目，也不从标题关键词自动推断故障、需求或因果。

```json
"change_relations": [
  {
    "id": "R1",
    "kind": "需求",
    "title": "搜索页完整展示服务端推荐",
    "summary": "首次实现和后续数量规则调整属于同一用户场景。",
    "status": "最终已取消客户端截断；代码和单测确认，设备待验证。",
    "steps": [
      {
        "commit_key": "c01",
        "kind": "需求",
        "summary": "首次接入推荐模块，按当时协议展示。",
        "file_ids": ["F001", "F002"]
      },
      {
        "commit_key": "c06",
        "kind": "需求",
        "summary": "数量规则改为由服务端决定，移除客户端截断。",
        "file_ids": ["F001"]
      }
    ]
  }
]
```

- `id` 为唯一的 `R1/R2/...`，是关系编号，不是 commit 编号；`kind` 在关系与每个阶段均必填，固定为 `修复/需求`。需求新增/调整用“需求”，已有行为违反已确认预期才用“修复”；需求中的后续缺陷修正阶段可标“修复”。没有独立依据时在 `summary/status` 明说待确认，不把规则变化倒推为历史 bug。
- `title/summary/status` 均非空，分别说明用户场景、关系原因与当前最终状态/证据确认度。支持只有一次实现的需求；原问题已被后续处理时必须说明，不能混进最终未修复问题。
- `steps` 非空；每阶段的 `commit_key/kind/summary/file_ids` 必填。`commit_key` 精确引用 manifest 中唯一 key（字母、数字、下划线、连字符；保留字 `final` 不可用作 manifest key）；`file_ids` 引用该提交快照的文件，不能跨提交复用同名 ID 当成同一版本。单范围有关系时使用 `commit_key: "final"`。
- 关系按首次代码变化顺序排列；每条的阶段按 manifest 顺序且同一提交在本关系中只列一次。一个阶段可列多个相关文件，读取其全部真实 hunk；一个提交可被多条关系引用，同一文件可以支撑多条关系。复用必须有实际共同作用，不能为了覆盖生造关系；展示实例 ID 含关系与阶段前缀，净增删统计仍来自最终冻结范围。
- `file_ids` 仅在对应提交没有任何 diff 文件时允许空数组；所有冻结提交及每个提交的全部 diff 文件均须被至少一条关系覆盖，文件内全部 hunk 的原始审查仍完整展开。不存在的 key/file、重复 ID、乱序、漏覆盖均拒绝生成。原数据的 `follow_up` 不能替代结构化映射；旧输入需人工补关系，不静默回退到旧布局。
- 基线已有问题可选 `origin: {"label": "origin/dev", "summary": "基线已有的具体机制及证据"}`，随后 steps 仅列范围内真实变化；不得给基线起因编造本分支引入 commit。撤回在阶段说明写实际撤回对象和最终状态。
- 新报告的完整审查外层默认收起；展开后关系下业务与辅助文件/hunk展开，测试行数统计独立、默认不纳入源码审查，批量开关和真实行号证据继续生效。最终完整 diff 保留全部净文件和语义明细；各阶段不重复铺全范围矩阵、验证总表或另一个只含跳转的全局关系表。

每项 `{ "title": "表名", "headers": ["列名"], "rows": [["单元格"]] }`。根据 `file-change-review` 报告合同保留表名和列；不得填空或用无关验证替代：

1. 当前改动影响范围与潜在隐患
2. 基线、约束与验证矩阵
3. 最小必要改动基线（目标依据、当前目标、最小充分链路、非目标）
4. 最小必要改动门禁（五项）
5. 功能点前后差异
6. 文件功能影响与丢失
7. 冗余/过度改动
8. 用户视角验证（各 F 的前提、动作、改前/改后、观察、状态；S→I→Oracle）
9. 待确认改动与验证边界

允许在有同类机械文件时列全路径合并；所有文件仍须覆盖。无冗余写“未发现确认的冗余或过度改动”，有待确认项另列。无用户直接变化仍写用户预期不变与验证依据。

`validations` 每项 `{ "name", "result", "layer", "oracle", "boundary" }`，分别写执行结果、源码/Mock/单测/契约/编译/设备/后台层级、实际判定标准、不能证明什么。未执行可显式列未验证，不能虚构命令或结果。生成器不会执行业务检查。

`validations` 保留为内部审查数据，不生成“本轮实际验证”“当前 HEAD 执行结果”等独立区域、汇总表或导航；不能改名、折叠或移到附录继续呈现同一内容。与问题结论有关的验证结果和缺口，在对应问题、文件或代码块旁简短说明并链接真实证据；不改变验证执行要求，也不删除有实际 diff 的测试文件区。

不渲染“审查依据与交付边界”独立区块或导航，也不以同义标题、折叠区或附录保留其整段过程总述。规则来源、采集/指纹核对、旧报告关系、已做/未做操作和浏览器限制等保留为内部记录；只把影响判断的证据限制简述在对应问题、文件或代码块旁，影响整体结论的必要限制可在结论一句话说明。
