# 文件与代码块危险系数

每次生成或更新审查报告时读取。分别给文件和独立 hunk/职责段打分，帮助用户决定先审哪里、审到多深；不能用评分代替语义审查、finding 或验证。

## 依据与适用边界

- [ASTQB：ISTQB Foundation 5.2 风险管理](https://astqb.org/5-2-risk-management/)：以发生可能性和损害影响指导验证优先级。本模型将业务后果/影响面与复杂度、兼容性、变更量、验证缺口等审查信号分开列明；后者只是可能性/不确定性代理，不能冒充测得的概率。
- [Google：代码审查应检查什么](https://google.github.io/eng-practices/review/reviewer/looking-for.html)：检查设计、功能、并发、复杂度、测试及上下文，关注过度设计；不能只看局部增删。
- [Google：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)：小而自洽的改动更容易审查；规模还受分散文件数和理解上下文影响，没有适用于所有改动的固定行数上限。
- [Microsoft Research：Relative Code Churn](https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/)：相对组件规模、时间等背景的代码变更指标在其研究数据上比单看绝对变更量更有预测价值，不能把该数据集的准确率外推到当前项目。
- [Microsoft Research：Dependences and Churn](https://www.microsoft.com/en-us/research/publication/explaining-failures-using-software-dependences-and-churn-metrics/)：依赖关系和代码变更共同提供故障倾向信号，支持检查公共消费者与影响面。

下列权重、分档和升级下限是**本 Skill 的默认启发式 v1**，不是以上来源提供的统一评分公式，也未经本项目历史缺陷数据校准。对单次报告使用同一版本，不为了得到期望颜色临时改权重；以后有项目校准依据再显式更新。分数不是“出错概率百分比”。

专业打分的最低要求：先有具体用户失败场景或必须保护的行为，再评估影响与触达消费者；六维理由绑定本次冻结代码/调用者/验证记录。不能从路径名、关键词、行数直接自动推断业务分、公共性或关键链路。维度有关联，不声称统计独立，权重只安排审查资源；披露重复影响的处理，不把测试通过、文档长度和产品执行风险混为一谈。历史 commit 与最终净差异分别评分，明确后续修复，验证依据限定到匹配的代码版本。

报告提供可折叠的模型说明与上述原始来源链接，各项评分可展开六维等级、理由、来源、适用下限和文件聚合依据。未来校准须按发布后的实际缺陷回溯命中率/漏报率、审查者一致性及分档区分能力，并显式变更模型版本；本次没有这类项目数据，不提供伪精确概率或研究准确率承诺。

## 六维评分

每维按实际证据取整数等级 0–4。分值为 `权重 × 等级 / 4`，相加后四舍五入为整数 0–100，再应用下文升级下限。每维附一句理由和真实来源（调用者、owner、协议、代码位置或验证记录），不能只贴“高/低”。

| 维度 | 权重 | 0 / 1 / 2 / 3 / 4 的判断锚点 |
| --- | --- | --- |
| 业务影响 | 25 | 无执行行为变化 / 局部展示或辅助功能 / 单个业务操作结果变化 / 核心用户旅程或关键数据变化 / 安全、身份隔离、资金、不可恢复数据等重大后果 |
| 公共复用与影响面 | 20 | 已证明隔离且无外部消费者 / 单一页面或局部调用 / 同 feature 多个真实消费者 / 多模块或跨平台共享 / 全局基础能力、公开协议或广泛消费者 |
| 已有功能与兼容风险 | 20 | 已证明旧行为不变 / 局部向后兼容扩展 / 相邻原功能或边界分支变化 / 改变原默认值、错误/重试/顺序/持久化或调用契约 / 不兼容迁移、广泛行为替换、关键数据/状态清理等 |
| 逻辑复杂度与范围耦合 | 15 | 纯机械且语义已核对 / 简单同步局部逻辑 / 多分支或局部状态转移 / 异步、并发、生命周期、跨 owner 协调 / 多重时序、资源所有权、跨端契约或难以独立回滚的耦合 |
| 改动规模与相对密度 | 10 | 无执行代码变化或已核对的纯移动/机械生成 / 通常1–10行局部增删 / 通常11–50行 / 通常51–200行 / 通常超过200行或实质整体重写；并结合真实所属函数/组件的重写密度调整 |
| 验证缺口 | 10 | 匹配风险的直接验证已覆盖 / 少量非关键边界未覆盖 / 主要依赖Mock、未覆盖相关消费者或异常分支 / 改动行为缺少有效回归，或平台/时序结果未测 / 匹配验证失败、关键证据缺失/矛盾或无法对账 |

补充判断：

- “位于shared目录”不自动等于公共风险，“只改1行”不自动低危；读取实际调用者、输入输出和控制条件。没有查到消费者不能当成“证明无消费者”。
- 文件和方法分别展示公共/私有作用域标识及影响范围，不能把文件标签复制给全部方法，也不能把模块内部export直接当公共API。私有方法仍可能经公共入口影响多个消费者，公共方法也可能只有一个当前消费者；本维按实际可达影响面评分，不能凭“私有”降分或凭“公共”直接判满分。作用域无法确认时保留待确认/评分区间。
- 行数取冻结 diff 的实际新增+删除，不含上下文和元信息。小函数大比例重写可提高规模等级；不能用 `@@` 的上下文长度冒充函数总长。读取不足时注明相对密度未知。
- 文件级评估用该文件的完整改动量与整体消费者；块级只看本块语义和它实际触及的共享契约，不机械复制同文件全部标签。
- 生成物、格式化和大规模删除不单靠行数判高危；也不能因“纯删除”忽略功能入口、schema、权限或兼容性丢失。二进制/mode-only无hunk时仍做文件级判断，未知行数不写0。
- 冗余/过度设计和扩大范围可增加复杂度、兼容风险或理解负担，但需有具体依据；这些必要性标签仍独立显示，不被较低运行风险分掩盖。
- 测试数量或无关测试通过不能降低验证缺口等级；仅可依据覆盖当前变更场景、消费者和失败/反向时序的实际证据判断。

## 高影响小改动的升级下限

升级需要明确触达位置和原因，不能只凭关键词。应用 `max(六维得分, 适用下限)`；多条下限只取最高，不重复相加。

| 已确认的触达条件 | 默认最低分 |
| --- | --- |
| 改变登录、首页Feed、埋点等关键链路的控制流、状态、时序或数据语义；仅文案/注释提及不算 | 60 |
| 改变被现有消费者使用的公共API、共享默认行为、数据/存储schema或跨端协议 | 60 |
| 改变认证/权限/账号隔离的安全边界，或涉及资金、不可逆数据丢失等重大后果 | 80 |
| 本范围已有确认的P0/P1问题 | 85 |

绿色测试只能减少“验证缺口”维度，不能抵消影响面/业务后果或绕过上述下限。关键链路标题按用户要求标红；评分徽标仍使用真实分档颜色，不能因标题标红伪造红色高分。

## 文件与块的汇总

1. 每个独立块先给六维理由和评分；单个hunk包含独立职责时可以在保留原patch的前提下分别说明，不隐藏其中的高风险段。
2. 文件再评估完整改动的公共消费者、组合行为与跨块耦合，得到文件自身分数。
3. `文件最终分 = max(文件自身分, 该文件最高代码块分)`。不使用平均分，不用大量简单块稀释一个关键风险块，也不把各块分相加造成大文件必然满分。
4. 不取全报告或commit的平均分替代逐文件/逐块评分；页首仍保持用户指定的紧凑分支/commit/行数概览。

## 颜色与审查建议

| 分数 | 等级与颜色 | 建议的审查深度 |
| --- | --- | --- |
| 0–24 | 低 · 绿色 `#087443`，浅绿背景 | 快速核对用户结果、完整diff和必要验证，仍需理解改动 |
| 25–49 | 中 · 黄色（深黄文字 `#805900`，浅黄背景） | 核对改动函数、直接消费者、原功能与失败分支 |
| 50–74 | 高 · 橙色 `#A34400`，浅橙背景 | 优先审查；追完整受影响链路、共享契约/状态与定向回归 |
| 75–100 | 很高 · 红色 `#B42318`，浅红背景 | 优先安排人工重点审查，核对跨模块/跨端影响、迁移与恢复验证 |

- 文件与块标题都显示 `危险系数 68/100 · 高`，折叠后可见，并附一句最主要依据，如“公共目录解析器，改变旧字段兼容，相关错误分支未验证”。六维明细可默认折叠，不新增用户已要求去掉的筛选功能或全局长表。
- 颜色之外必须有数字和文字等级，保持对比度，不能只靠红绿区分。保留原有用户场景标题、`+新增/-删除`、关键链路 `‼️`、大段 `⚠️` 和冗余/范围标签。
- 不得把低分写成“无需审查/自动通过”；用户据分数安排顺序和深度，评分本身不产生免审、批准或发布授权。

## 危险系数驱动展示顺序

- 文件按最终危险系数降序，文件内部代码块按各自危险系数降序，让高风险改动先被看到；同分采用稳定原顺序。存在明确commit分组或业务/辅助/测试独立分区时，范围内分别降序，并如实标明排序范围。
- 分数区间按上界优先安排，但仍显示完整区间/待补证；未评分单独置于待评估的优先位置，不能默认0分归到末尾。
- 文件自身分和最高块分的汇总规则保持不变；不能为了排到前面抬分，或用平均分改变排序。
- 排序只影响阅读呈现。冻结的文件/hunk身份、原始patch、行号、指纹及问题证据引用保持原样；复制/下载原patch不按风险重排。

## 信息不足与确认度

- 不知道公共消费者、旧行为或验证结果时，不能记0分或凭感觉给低分。对未知维度按0–4计算可能范围，展示如 `危险系数 45–75/100 · 待补证`，说明缺什么；审查安排可参考上界，不能把上界当已确认风险。
- 区间应用同一升级下限；文件对分数区间的上下界分别取其自身和各块的最大值。一个未知块不能被其它已评分块冲掉。
- 只有足够证据选定各维等级时才显示单一分数。`高/中/低置信度`与分数分开说明：置信度高只代表评分依据清楚，不表示代码安全或存在缺陷。
- finding的P0–P3、代码/测试/运行证据和发生频率仍独立记录；评分不能制造finding，也不能把Mock机制写成设备实锤。

## 校准示例（假设场景，不是实际项目结论）

- 隔离组件的少量文字样式变化：可得到低分，但要有隔离消费者及原功能不变的依据。
- 只改1行登录资格判断：即使规模维度低，只要改变关键控制流，至少60；若改变安全边界则至少80。
- 公共parser改变已有错误/默认值语义：即使仅十余行，至少60；必须核对已有消费者与回归。
- 某文件普通块12分、关键块82分：文件不能平均成47，至少82；若文件组合影响更大可更高。
- 纯文档/已确认机械生成不能只因大段增删被判高危；反之，缺少调用链/验证信息时不能只因行数少给绿分。
