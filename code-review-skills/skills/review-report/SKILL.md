# 审查报告

把代码审查变成可决策、可逐文件逐块复核的单文件 H5。先读[案例记忆](memory.md)中的关注模式，再按本次风险/交接阶段读取相关案例，不通读所有历史。关键词 **审查报告**是本技能的触发词，保持自动选择开启；也可显式调用 `$review-report`。

## 审查与说明 owner

- 执行包内 [file-change-review 方法](references/file-change-review.md)，按其审查流程和 [报告合同](references/file-change-review/report-contract.md)取得逐文件结论、功能差异、必要性、影响与验证映射。本技能负责冻结 diff 与呈现，不用生成器代替审查判断。
- **审查问题必须执行包内 [plain-language 方法](references/plain-language.md)**，读取其 H5 规范。每个 P? 用用户能观察的表现、影响、操作、实际/预期结果、关键原因和确认状态说明；保留代码/测试/设备证据边界。问题说明嵌入本报告，不另生成重复页面。`assets/report.css` 基于该技能 H5 模板扩展，问题卡片与 diff 使用同一套证据编号。
- 本包已内聚上述方法与模板，无需另装这两个 Skill。包内资源缺失时报告安装损坏，不假称执行成功，也不用美化页面补充事实。
- 业务仓库只读。生成文件放到用户指定的仓外目录或宿主 artifact/visualization 目录；不 stage、commit、push。设备、模拟器、服务与外部系统操作由使用者当次指令及当前项目合同决定；本包不携带任何个人的永久授权。另有修复、构建安装或服务操作时按已有授权范围处理，不由模拟器验证自动扩展权限。

## 呈现重点

- **修复回填标清双基线（用户确认）**：保留原 P?、历史版本与证据，另标当前修复状态及代码/测试/运行层级。修复区明确展示“修复前 → 修复后”和“冻结目标分支 → 修复后”两份完整业务 diff，双方 hash、文件范围与旧/新行号就近可见；逐处区分新增逻辑、修改与既有上下文。两份 patch 相同也保留比较身份并说明已核对的原因，不能推广到其他文件或宣称全分支已重审。最终源码高亮图标为“修复后源码／关键行高亮（非 diff）”，不能让绿色高亮替代真实增删判断。
- **字段疑问就近给可核对结论**：读者质疑“只是改名”“旧变量名是否代表旧业务身份”时，沿 [judgment-analysis 的字段语义核验](references/field-semantics-evidence.md)核对后，将逐断言结论、最小字段映射、读写证据与置信边界放回同一问题卡。方法细则由该 owner 维护；本报告不另建方法论总述或验证汇总，不用源码、diff、截图的重复呈现抬高独立证据数。

- **测试代码跳过审查，仅记录改动代码行数（用户确认）**：默认不审查测试源码、测试脚本及专属测试支撑，不读取或展开其 diff，不填写必要性、危险系数、覆盖说明或审查结论。仅按文件路径列出 `+新增 / -删除` 行数及测试合计；新增与删除之和可另列为变动总行数，不能当作净增量。测试统计与业务审查统计分开，明确标“跳过审查”，不把行数记录写成测试通过。完整文件/hunk 审查、关系覆盖、评分和 patch 展示要求仅适用于纳入审查的非测试文件；测试只校验清单与行数。用非测试路径生成审查快照，另用同基线、同范围的 `git diff --numstat` 记录测试行数；未跟踪测试文件按新增真实行数统计，二进制行数标“未知”。现有生成器无需为测试补虚假审查字段：测试统计保存到独立数据，在 `focus_review_html` 的单独紧凑区域展示。用户明确要求审查某测试文件时，才将指定测试重新纳入完整审查。

- **全量审查与人工/AI分层**：先实质审查全部纳入的非测试文件及hunk，再按[人工结论与完整AI复核合同](references/focus-review.md)呈现。前层先说整个分支改什么、改前改后、测试关注/通过标准，再给确认问题、高关注通过项及读者动作；用 ✅/❌/⚠️ 绑定对象、版本和证据层级。确认问题只维护一张主卡，不再重复“重点与争议”。关键原因旁默认显示必要源码图/行号与解释；全部逐项判断和原始diff默认折叠，标「🤖 给 AI 二次复核／人工按需查证」，不能删除或只留侧车JSON。启动、公共埋点、测量、映射与大块公共改动的通过项也主动给影响边界；具体方法归[file-change-review](references/file-change-review/impact-and-evidence.md#high-attention-changes)。
- **人审回传与飞书交接**：侧会话按关注点去重，记录认可范围、基线、证据和实际阶段；仅登记不写成原报告已更新。用户要求飞书报告/同步时读取[飞书交接参考](references/feishu-review-handoff.md)，正文直接承载必要沟通截图、规则原文与关键证据，不依赖读者点链接；不自动发送或新建侧会话。

- **风险与双端一致性仅在异常时展开描述（用户偏好）**：“补充风险与验证边界”经审查没有需提示的风险或影响判断的证据缺口时，仅显示“无”；“另一端逻辑是否一致”已确认双端一致时，仅显示“一致”。其余情况才补一句精简说明，直接点明风险、差异或待确认项，不重复实现过程、历史阶段摘要和通用免责声明。没有确认问题不自动等于无风险，未核对另一端不自动等于一致；影响判断的验证缺口仍须在对应项简短保留。`risk` 与 `pair` 保存展示摘要，完整依据分别放入可选的内部 `risk_detail`、`pair_detail`，不在这两项重新铺长段；有独立 P? 的问题仍保留原有可见入口。

- **文件层需求说明合并、最小改动独立判断（用户偏好）**：文件审查原“改动用途 / 为什么要改 / 不改动有什么影响”合并为一项“需求文档中需求描述”，默认只用一两句话说明对应需求、用户场景和预期结果；不能把各 hunk 的用途、机制与反事实拼成长段。需求来源及这三项完整补充说明放在默认折叠的“展开补充说明”中，内部审查数据仍保留。新增独立项“是否符合最小必要改动”，逐文件给出 `符合 / 部分符合 / 不符合 / 证据不足` 及简短依据；判断覆盖直接实现、必要支撑和必要验证，不能用“必要”或测试通过代替最小性结论。需求未明确要求的改动（包括必要支撑）必须就近给出可见的合理性说明，指出与目标的关系、不能省略的原因及最小收口范围；缺需求文档标“需求依据缺失”，不得把 commit 描述或代码实现冒充需求原文。使用 `requirement_context` 和 `minimum_change` 保存人工判断，字段合同见 references/report-data.md；旧数据兼容展示时保留缺口，不自动编造需求或最小性结论。

- **直接按修复或需求关系展开代码（用户偏好）**：完整逐项审查层为 `关系条目 → 代码演变阶段（按冻结提交顺序）→ 本阶段文件 → diff 与分段分析`，从前层重点或完整审查入口展开。每条标题标 `修复` 或 `需求`，说明用户场景、变化原因和当前状态；阶段也标类型，避免把需求首次实现、后续需求调整和缺陷修复混为一谈。展开完整审查后，相关业务/辅助文件及 diff 分析在本条下展开，可收起；测试仅保留独立行数统计，不进入关系条目的代码审查。不把关系放一处、代码另列一处再要求读者跳转拼接。保留最终完整 diff 入口。
- **关系随真实代码变化，不能按 commit 数凑项**：`R1/R2/...` 是稳定关系编号，明确区别于 commit 哈希和总数；一条关系可跨多个 commit，一个 commit 也可支撑多条关系，只有一次实现的独立需求也应有条目。同一关系内标明首次实现、需求调整、修复或撤回的实际哈希与结果；起因在比较基线时注明基线来源，不伪造范围内引入提交。每个冻结 commit 中纳入审查的所有非测试 diff 文件及块必须至少被一条关系覆盖；同一文件跨关系复用时保留各自提交身份，不把重复展示累计成净变化量。用结构化 `change_relations` 填写人工确认的关系，不从 commit 数、subject 关键词或 diff 自动猜测需求与根因。历史问题不能冒充最终仍存在的问题。
- **不展示审查依据与交付边界总述（用户偏好）**：删除“审查依据与交付边界”整块说明及导航；不改名、折叠或搬到附录保留同一内容。不集中铺陈读取了哪些规则、如何重新采集/匹配指纹、旧报告关系、执行或未执行哪些操作、浏览器访问限制等过程说明。内部审查约束和记录仍保留；确实影响问题判断的证据限制，在对应问题、文件或代码块旁简述，整体结论必需的限制只在结论用一句话点明。
- **不展示独立验证汇总（用户偏好）**：删除“本轮实际验证”“当前 HEAD 执行结果”及对应整张验证结果/层级/判定 Oracle/未覆盖边界汇总表和导航入口；不改名、折叠或移到附录继续展示同一内容。实际验证仍按需要执行并记录，`validations` 与原始证据保留；与结论有关的结果和缺口只在对应问题、文件或代码块旁简短说明，不重复铺表。有实际 diff 的测试文件仅保留独立行数统计。
- **确认问题紧接结论（用户偏好）**：报告顺序为紧凑概览/结论与业务主线 → 人工区确认问题及高关注判断/动作 → 默认收起的完整AI逐项审查。确认问题在人工区独立说明用户表现、影响、触发条件和证据状态，紧接结论且先于长diff；同一问题的主卡、复现路径、实际/预期结果及最小源码证据留在完整审查折叠层之外，额外证据可在主卡内折叠；问题按严重度优先，同级再参考危险系数。确认度与是否设备验证分别标明，代码/测试确认不能写成模拟器已复现，疑似项不能升格为确认。没有确认问题时不生成空问题区，在结论简述即可；关键原因所需最小源码证据默认可见，额外代码可折叠并保留定位。
- **只展示有diff的文件分区（用户偏好）**：业务、辅助、测试等区域在当前commit/范围没有实际差异文件时，整块不生成，包括标题、`0个文件/+0/-0/0个代码块`统计、说明、“本范围无此类改动”提示及对应导航。有diff时仍按原规则展示，测试保留独立的文件路径和增删行数，不能误解为不统计测试改动。是否为空按冻结范围内有无实际差异判断；rename、mode-only、binary等真实变更不能仅因没有文本hunk而被当作空区隐藏。
- **滚动时保留关系与文件身份（用户偏好）**：关系标题仅在所属关系范围吸顶，下层文件头按实际关系头高度避让，下一关系自然接替。阅读展开的diff时，对应文件标题区域应在该文件范围内吸顶，持续显示正在查看的文件路径/名称，并保留公共或私有标识、危险系数与必要改动统计。滚到下一文件时切换为新文件标题，不累积悬挂多个文件头；标题保持紧凑，不能遮住代码、行号、问题定位或锚点目标。长路径需仍能辨认具体文件并查看完整路径。
- **文件和块按危险系数降序（用户偏好）**：代码diff的文件列表按文件最终危险系数从高到低展示，每个文件内部的代码块也从高到低，不再只沿路径或源码顺序排列。另有用户指定的commit分组或业务/辅助/测试独立分区时，在对应范围内执行同一降序规则，并明确排序范围，不把分组内排序称为跨组全局排序。同分稳定保留原顺序；评分区间按上界安排审查并保留待确认，尚未评分不得当0分放到低风险尾部。排序仅改变呈现，不改快照、原始patch、hunk ID、旧/新行号或证据锚点。
- **文件与代码块都展示危险系数（用户偏好）**：生成报告前读取 [危险系数评分规则](references/risk-scoring.md)，分别评估每个文件与独立 hunk/职责段，在标题显示 `危险系数 68/100 · 高` 及对应颜色，折叠后仍可见；附一句主要得分依据，明细按需展开。默认按业务影响25、公共复用20、已有功能回归20、复杂度15、改动规模10、验证缺口10评分；颜色和审查建议按引用规则统一。文件不取各块平均数，至少保留最高块风险；关键链路/公共契约等小改动不能因行数少被判低危。缺证据保留区间/待确认，不编造精确低分。此为本 Skill 参考行业资料制定的启发式审查优先级，不是行业统一标准、故障概率或免审/approve结论；与关键链路标红、`‼️`、`⚠️`、冗余/范围标签和问题严重度分别保留。
- **公共/私有影响范围分别标识（用户偏好）**：文件标题标 `公共文件`、`私有文件` 或 `范围待确认`；对应方法/函数或其代码块标题另标 `公共方法`、`私有方法`、`公共/私有方法混合` 或 `范围待确认`，折叠时也可见。这里的公共指当前审查边界外可用的接口、共享能力或跨页面/模块消费者，私有指内部实现且调用范围已确认局限于所属文件/组件/模块；按 public API、导出/可见性、实际调用者与间接影响共同判断，不能仅凭 shared/private 目录、export 关键字或命名定性。文件与方法独立判定：公共文件中的局部 helper 可是私有，私有 helper 也可能经公共入口影响所有调用者。简注共享给谁/局限在哪里，并计入危险系数的公共复用与影响面，不把“私有”当成无回归风险。非方法代码块说明所属作用域，不强贴方法标签；缺依据明确待确认。
- **页首概览合并、保持简短（用户偏好）**：将顶部改动统计与“基线/目标”合为一个区域，默认只说清当前分支、对比的目标分支、commit 数及增删行数。例如：`feature/example → origin/dev · 11 个 commit · +1066 / -272 行`。非分支范围按实际对象显示，不虚构分支或 commit 数；增删行沿用冻结 diff 的统计口径。
- checkout 路径、完整 HEAD/base/共同祖先 SHA、range 解释、采集时间、指纹、工作区三层清单，以及文件/业务测试/代码块等详细统计，保留在**默认折叠的审查详情**或相应文件区域，不再另铺一张冗长基线卡，也不在页首重复统计。问题结论仍单独清晰呈现；精简概览不删除证据、不混淆比较方向或两点/分支自身差异。
- **不生成重复的关系总表**：修复/需求条目本身就是代码审查的主入口，其下直接承载相关 diff；不再额外生成只有哈希跳转的“后续修复／撤回关系”“提交演变”汇总表，也不恢复“先辨清两种差异”过程说明。关系条目上的状态、类型与代码就近展示，不能以本条误删主视图中的修复/需求关系。
- **不提供文件筛选（用户偏好）**：去掉路径/旧路径搜索、类型下拉、“只看关联问题”等筛选控件及筛选计数、无匹配提示；每个 commit 和最终范围都完整展示所属文件。文件展开/收起、业务与辅助文件批量展开、代码换行及问题证据跳转继续保留，不为删筛选而减少审查覆盖。
- **代码块标题直接展示本块改动量（用户偏好）**：每个 hunk 标题带实际新增/删除行数，例如 `代码块 1 · 没有可用头像框时显示空态 · +1 / -0 行`；需要合计时使用新增与删除之和，不把上下文行或 `@@` 范围长度算作改动。遇到大段新增、删除或重写，在同一标题显式加 `⚠️ 大段改动`，使折叠时也能识别；不能用整文件规模代替本块规模。该标识只提示重点阅读，不等于已确认缺陷或 P? 优先级，用户未指定的预警阈值不得写成其已确认规则。
- **代码变更先从用户视角说明（用户偏好）**：代码块标题与“改动用途”先写用户在哪里、执行什么操作、会看到或得到什么结果；对应按钮使用实际文案。函数名、ref、状态 owner 和调用顺序放在位置/机制/证据说明，不用“消费目标”“先 dismiss 再 router.push”等内部术语代替用户场景。内部支撑块说明它支撑哪条用户操作，用户操作或表现不变时明确写不变，不给每个 helper 虚构独立入口。涉及前后差异时绑定同一场景和可核对基线；没有运行证据，不把预期效果写成已经观察到的改善。
- **关键链路改动标题标红预警（用户偏好）**：改动触及登录、首页 Feed、埋点等关键链路时，对应文件标题和命中的代码块标题使用红色，并显式加 `‼️ 改动登录关键链路，仔细审查`、`‼️ 改动首页 Feed 关键链路，仔细审查`、`‼️ 改动埋点关键链路，仔细审查` 等具体文案；多条链路逐项点明，折叠状态也可见。按实际改动与执行链判断，不因文件名或未修改的上下文出现关键词就标记；混合文件只给确实触及的代码块标红，文件标题汇总所涉链路。保留用户场景标题、增删行数及大段修改的 `⚠️`，不互相替代。`‼️` 提示审查重点，不代表已有确认缺陷、P? 优先级或审查通过。
- **每块必要性可见，非必要块黄色预警（用户偏好）**：每个独立 hunk 标题直接显示人工填写的 `必要性：必要/有条件必要/冗余/过度改动/证据不足`，折叠后仍可见。确认 `冗余` 或 `过度改动` 时，标题与审查信息区使用黄色背景，并显示 `必要性：⚠️ 非必要 · 冗余/过度改动`；不能只在长说明或总表中提示。高疑似、条件未证实和证据不足保留限定语，不自动当成确认非必要。按块判定，不把同文件其他必要改动连带标黄；给出真实消费者、既有门槛、反事实移除影响及最小收口建议。已有 `冗余/过度设计/额外重构扩大范围` 标签、关键链路红字 `‼️`、大段改动 `⚠️` 与原 diff 增删红绿独立保留，黄底不覆盖代码行颜色。
- **多个独立目标必须按 1、2、3 有序列表逐项换行展示**，每个目标独立一条，不用分号拼成长段。`review.goal` 使用字符串数组表达各目标；单个目标可直接显示。旧版单目标字符串继续兼容，旧版长段须人工按真实目标拆分，不由生成器按标点猜测。

- **业务审查与测试行数使用独立区域和独立文件清单，业务在前，测试统计在后**；不能仅加分类标签或依赖“文件类型”筛选来分开，也不能让路径排序把测试排到业务代码前面。
- 业务代码是报告主体，保留逐文件结论、功能差异、必要性、合理性、风险、完整 diff 与逐块解释。配置、文档、生成物及其他辅助文件单独展示，保留各自分类。
- 测试只列文件路径与新增、删除行数及合计，标明跳过审查；不展示源码、逐块解释、覆盖内容或测试实现评价。已取得且与业务结论有关的实际执行结果可在业务问题旁简述，不从测试行数或文件名推断覆盖和通过。
- 业务审查统计与测试行数统计分开，测试不统计审查代码块、不评分、不生成测试 P?；业务与辅助文件的批量展开不包含测试。
- 完整审查覆盖与完整 patch 导出仅针对明确纳入审查的非测试范围；另存测试行数清单、比较基线及范围，不能删除测试统计后声称已覆盖全部改动。

## 执行

### 观察力Agent 发起的审查

当用户从观察力Agent点击“代码审查”，且当前会话提供冻结 `snapshot.json`、任务标识与 `submit_review_report` 专用工具时，先读取 [观察力Agent 接入合同](references/observation-agent.md)。沿用本技能全部实质审查、测试跳过、评分和完整性要求；直接消费给定快照，填写结构化审查结果并通过专用工具回传，由观察力Agent调用正式生成器保存 H5。此入口不重新采集/覆盖快照、不写被审仓库、不自行执行测试或操作设备；不能用最终聊天消息代替回传。普通审查报告继续使用下方流程，无专用工具时不得假称已接入观察力Agent。

### 冻结完整输入

确认当前 checkout、branch、HEAD 和 dirty 状态，保留已有改动。按用户指定对象选择范围；未指定而要求“当前改动审查报告”时使用 `worktree`（HEAD 到当前工作区，包含 staged、unstaged、untracked），记录三层文件清单。分支/range 必须明确 base/target，不自动 fetch 或把本地状态叫作“最新远端”。

生成器使用 Python 3.10+ 标准库与 Git，无 Python 第三方依赖。发布包每次调用先执行生成的 scripts/entry.mjs，并固定回执中的 version、workflowPath、resourcesRoot；以下所有 scripts/assets/references 相对路径均以该 resourcesRoot 为准，不能回到旧安装目录找资源。以下路径是示例参数，替换成实际路径：

```bash
python3 /path/to/review-report/scripts/collect_diff.py \
  --repo /path/to/repo --scope worktree \
  --output /outside/repo/snapshot.json \
  --review-template /outside/repo/review.json
```

- 其他范围：`--scope staged`、`--scope unstaged`、`--scope range --base <ref> --target <ref>`；`--path <仓库相对路径>` 可重复。详见 [数据与命令合同](references/report-data.md)。
- 快照保留所有纳入审查的非测试文件、完整 patch、每个 hunk、旧/新总行数、增删行、分类依据与内容 hash；测试另存同范围行数统计。分类是启发式，必须人工确认；测试脚本不能只因源码后缀就算业务。
- 输出默认不能位于被审查仓库内。模板已存在时换新路径，避免覆盖审查注释。敏感文件需缩小范围或显式 `--exclude` 并在报告列明排除；同时人工检查正文与 diff 是否有密钥或隐私。不得静默省略后声称全量覆盖。
- 输入并发改变时采集失败。审查期间输入变了就重采受影响范围并重核结论，不能把旧快照与新代码混合报告。

### 逐文件与逐代码块审查

读取基线版本、当前上下文、实际调用者、状态 owner、失败与清理路径，按 `file-change-review` 填写 `review.json`；生成报告前读取 [数据与命令合同](references/report-data.md)。

每个纳入审查的非测试文件都说明用途、改动位置、实现结果、独立目标依据、不改的具体影响、必要性、合理性、功能丢失结论和风险。业务审查与测试行数分类分区，测试跳过审查；配置、文档、生成物单独标识。原生文件核对另一端真实契约，不按语法相似推断一致。

**每个独立 hunk 都有贴近代码的解释**：改了什么、为何必要、为何实现合理、保留其他改动而移除这一块会失败什么、证据与关联 P?。问题关键行通过 `focus` 指定真实旧/新行号、数字标记及“证明什么”的解释，完整 diff 继续保留。同文件不同块可得不同必要性结论。新增文件可能只一个大 hunk，按函数/职责需要可在解释中继续分段，不省略原 diff。

新增或收紧加载/就绪、空值拒绝、guard 等保护的块，必须按 [已有门槛与防御改动](references/file-change-review/scope-and-necessity.md#已有门槛与防御改动) 逐项核对生产入口、各消费者原有资格、新判断额外拦住的真实可达路径，以及拒绝结果是否被调用方消费。分别写入本块的 `reasonableness/evidence/without`；不能用假设绕过上游、直接调用 helper 的新增测试证明必要性。消费者被撤回后重新审查 helper、导出和类型放宽；专属测试仍仅统计行数。生成器仅按人工 `necessity` 渲染黄底和警告，不从路径、风险分、关键词或测试通过推断是否必要。

已有生产者已满足目标输入、只需扩展消费者，或准备类推另一平台/相邻实现时，先执行 [已有能力与同类代码的范围判断](references/file-change-review/scope-and-necessity.md#已有能力与同类代码的范围判断)。独立修复有效但不属于当前目标的块按 `过度改动` 显示黄色背景和 `⚠️ 非必要`；没有独立贡献的块按 `冗余`。不能以测试证明额外修复有效，就把它写成当前需求的必要支撑。

解释以读者能核对为准：新增参数/状态写清来源、创建 owner、传递链和失效条件；“兼容旧接口”要有当前调用者或发布契约依据；测试存在不证明生产消费者存在。键、来源快照、对象持有及清理等机制仅在实际触达时检查，不套用某个项目的历史问题。弱引用不等于元数据无增长，消息到达时快照也不自动证明原文档身份。

所有问题用唯一 P?，分别标优先级、证据等级、频率。用 `plain-language` 写用户复现路径；代码调用链放证据，不冒充用户操作。未执行写“候选复现路径/待验证”，没有在线归因证据不得从机制或 Mock 成功外推线上占比。无确认问题不等于无风险，证据不足照实保留。

完整保留 `file-change-review` 的强制表与功能/场景/原行为/验证映射，写入 `sections`。生成器只核验结构与 diff 对齐，不判断门禁是否满足或结论是否正确。

### 生成与验证

新报告使用 `scripts/render_compact_report.py`：`--snapshot <冻结快照> --review <含人工评分的审查JSON> --output <仓外HTML>`；分支多提交另传 `--commits <manifest.json>`。manifest 为有序数组，每项包含 `key/commit/subject/snapshot/review`，后两项相对 manifest 所在目录；可附合并继承 `inventory`。多提交必须在总 `review.json` 提供 [数据合同](references/report-data.md#修复需求关系与就近代码演变) 的 `change_relations`，引用真实 commit key 和该次快照的 file ID；非分支单范围可用 `final` 引用本次变化。生成器拒绝关系缺失、引用悬空、阶段乱序及提交/文件漏覆盖，不自动推断关系。它同时复用快照、逐块和证据校验，并核对评分、风险排序和原始 patch 导出；未提供评分不得作为新版正式交付。原 `render_report.py` 只保留数据兼容与内部校验。

**按当前项目授权验证**：只有使用者当次指令或当前项目合同已授权设备验证时，才核对设备空闲、平台、安装包和实际运行源码身份，再执行最小相关路径。同一设备只有一个操作方，“已启动”不代表空闲。没有授权时保留设备验证缺口，继续静态审查；维护 Skill 本身不启动设备。

记录实际操作、场景/时序、结果、截图或日志以及对应代码身份。模拟器结果只证明已执行的平台、版本与条件；代码、单测、Mock、模拟器和后端证据分别说明。未复现应列出已执行条件与覆盖边界；设备占用、驱动失败或代码身份不匹配记为受阻/未验证，不能记为无法复现。没有可用模拟器时保留验证缺口，继续审查。

```bash
python3 /path/to/review-report/scripts/render_compact_report.py \
  --snapshot /outside/repo/snapshot.json \
  --review /outside/repo/review.json \
  --output /outside/repo/report.html
```

填写前需要草稿预览时使用兼容入口 `render_report.py --draft`，页面明确标“草稿/待填写”，不能以草稿交付。新版紧凑入口只接受正式且含完整人工评分的输入，拒绝缺少文件/hunk 解释、评分算术错误或指纹不匹配的输入。

报告必须包含：

- 从全部非测试审查记录提炼的人工业务主线、确认问题/高关注结论与行动，以及默认收起、完整保留的AI复核层；不再重复“重点与争议”，不能先挑热点再补模板句冒充全量已审。

- 基线、目标、证据边界、逐文件结论和问题概览；问题直接跳到对应代码。
- 独立的业务、辅助审查清单及测试行数清单，业务优先。业务与辅助清单保留状态、旧→新总行数、增删行、hunk 数及覆盖信息；测试仅列路径、`+新增/-删除` 与合计并标明跳过审查。二进制无法计数显示“未知”，不算 0。
- 全部纳入审查的非测试 diff 代码：旧/新行号、红绿及 +/- 文本、必要上下文、rename/mode 元信息；文件和代码块都可展开收起，有业务与辅助文件批量展开、全部收起及代码换行开关，不提供路径/类型/问题筛选；测试代码不嵌入报告，仅保留独立行数统计。
- 每块代码旁的必要性、合理性、反事实和证据解释；问题的用户表现、影响、复现步骤、实际/预期、建议与确认状态；实际验证结果与剩余缺口。

交付前按 [验收清单](references/acceptance.md)核对完整性、行号、统计、证据编号、离线与窄屏。用可用且允许的浏览器打开检查；若本地文件访问受环境限制，不绕过限制，执行静态检查并明确视觉/交互验收未完成。只报告实际检查结果，业务代码保持原样。

最终回复简短给报告绝对路径、关键问题及验证边界。用户只要求新建或更新本技能时，交付技能入口与实际验证结果，不自动更新业务报告或修复业务代码。
